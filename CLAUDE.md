# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

voltIQ is an offline native SwiftUI iOS 16+ port of the web app [PrahasM/voltIQ](https://github.com/PrahasM/voltIQ) (an EV charging calculator, profiles, operators and charge history). There are no package dependencies, server or network calls. The calculation engine must stay in parity with the web `script.js` (see README "Calculation parity" for the formulas, GST rules and rounding).

## Commands

```sh
swift test                                   # portable Core + test suite on macOS (fast, no simulator)
swift test --filter CalculatorTests          # one test class (or CalculatorTests/testName)

xcodebuild -project VoltIQ.xcodeproj -scheme VoltIQ \
  -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build     # also typechecks all SwiftUI

xcodebuild -project VoltIQ.xcodeproj -scheme VoltIQ \
  -destination 'platform=iOS Simulator,name=iPhone 16' CODE_SIGNING_ALLOWED=NO test   # app-hosted tests

git diff --check                             # whitespace lint (no other linter configured)
python3 tools/generate_project.py            # regenerate VoltIQ.xcodeproj after adding/removing source files
python3 tools/generate_icon.py               # regenerate app icon (needs Pillow)
```

Use `xcrun simctl list devices available` to pick a simulator name. CI (`.github/workflows/ios.yml`) runs `swift test`, the app build, then the Simulator tests.

## Architecture

- `VoltIQ/Core` is Foundation-only and is the SwiftPM target `VoltIQ` (`Package.swift`), so it also builds and tests on macOS. **Do not import SwiftUI/UIKit in Core.** The same files are compiled into the Xcode app target.
  - `ChargingCalculator.swift`: pure engine (target %, budget and time modes; DC taper phases; GST handling).
  - `Models.swift`, `ChargeLog.swift`: Codable models, compact web-compatible charge-log keys, CSV export.
  - `DeviceRepository.swift`: persistence of the versioned state envelope in `UserDefaults["voltiq-state-v1"]` and receipt JPEG files in Application Support.
- `VoltIQ/AppStore.swift` is the observable coordinator for persisted per-driver profile changes; views go through it rather than touching the repository.
- `VoltIQ/Views` holds the SwiftUI screens and `Theme.swift` (colors match the web hex values, light/dark).
- `VoltIQTests` is shared: the SwiftPM test target runs it on macOS, and the Xcode scheme runs it in the Simulator. Keep tests free of UIKit-only APIs where they target Core.

## Things to know

- Charge-log JSON keeps the web's compact keys (`t,e,c,r,g,k,b,s,f,y,o,oi,d,m,fe,x,q,p`); optional fields are omitted when absent, and legacy entries with only `t,e,c,r,g,k` (including empty-string `k`) must still decode. Don't rename keys.
- All settings, operators and logs are per driver profile; deleting a driver deletes their logs and receipts. Each driver keeps at most the latest 500 logs.
- Logged `cost` excludes session/idle fees; effective rate and history averages follow the web definitions in the README.
- The Xcode project is generated by `tools/generate_project.py`; hand edits to `project.pbxproj` will be lost on regeneration, so update the script when project structure changes.

- Charger discovery: `ChargerProvider` implementations (`MapKitChargerProvider`, `GooglePlacesChargerProvider`) return `RawStation`s; `StationNormalizer` validates/dedupes them and groups connectors by (type, power). Connector data comes only from Google Places; `ChargerProviderFactory` falls back to MapKit when `Config/Secrets.xcconfig` has no `GOOGLE_PLACES_API_KEY`. Availability, provider and price are shown only when a provider supplies them (otherwise labelled unavailable, never guessed). `ChargePlanner` (pure) preselects the connector and builds the "Charge Here" estimate from the driver's prefs; voltIQ never starts sessions or payments, only shows an in-app MapKit route (`RouteViewModel`/`RouteMapView`, an `MKMapView` wrapper because SwiftUI `Map` can't draw routes on iOS 16) or hands off to a provider app when a URL is known.

## User Story Development Workflow

When implementing product features, work on ONE user story at a time.

### 1. Understand Before Coding

Before modifying code:

- Read the assigned user story completely.
- Inspect the existing implementation and architecture.
- Identify existing components that should be reused.
- Identify files that need to be changed or created.
- Identify dependencies, APIs and permissions required.
- Identify tests required by the acceptance criteria.

Do not modify code during this step.

### 2. Produce an Implementation Plan

Before implementation, provide:

- understanding of the requirement
- affected components/files
- proposed implementation
- data flow
- tests to be created
- assumptions
- risks
- anything that is unclear

Wait for explicit approval before modifying code.

### 3. Scope Control

Implement ONLY the assigned user story.

Do not implement:
- future user stories
- unrelated refactoring
- speculative features
- unnecessary architecture changes

If another change appears necessary, explain it and request approval.

### 4. Implementation

Follow the existing Voltiq:
- architecture
- naming conventions
- UI patterns
- design system
- error handling
- dependency patterns

Prefer extending existing components over duplicating functionality.

Do not introduce new dependencies without explaining why.

Never hard-code:
- API keys
- credentials
- tokens
- secrets

External services must be isolated behind appropriate service/provider abstractions.

### 5. Testing

Every acceptance criterion must be testable.

Where appropriate create:
- unit tests
- integration tests
- UI tests
- error/edge-case tests

Run existing tests to ensure there are no regressions.

Build the application before declaring the story complete.

### 6. Acceptance Criteria Validation

At completion, report each acceptance criterion as:

PASS
FAIL
NOT TESTED

For every PASS, explain how it was verified.

Do not mark an acceptance criterion PASS merely because the code was implemented.

### 7. Completion Report

At the end provide:

- files created
- files modified
- tests added
- test results
- build result
- acceptance criteria results
- known limitations
- manual testing required

Then STOP.

Do not begin another user story until explicitly instructed.
